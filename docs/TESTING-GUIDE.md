### 0.4 四个"坑"（不知道就会得出错误结论）

这四条是真实踩过的，会让测试结果失真：

1. **视口必须设成桌面尺寸**。无头浏览器默认 800×600，会命中 CSS 的 `≤980px` 窄屏规则把左栏 `display:none`，
   取色器与工具面板就没有布局尺寸，所有拖动/点击断言都会失真。用 `Emulation.setDeviceMetricsOverride` 设
   1400×900，并断言左栏宽度 > 100。
2. **隐藏元素的 `getBoundingClientRect()` 全是 0**。`display:none` 的行做"不重叠""可拖动"断言会**假通过**。
   凡是几何断言，都必须同时断言尺寸非零。
3. **无头浏览器下合成的 `.click()` 不触发聚焦**，只有真实鼠标点击才聚焦。
   要验证"能否编辑"用 `element.focus()` + `document.activeElement === el`，不要用 `.click()`。
4. **`requestAnimationFrame` 在无头/后台标签页可能永不回调**，画布绘制是异步的。
   断言画布内容要**轮询**（项目里用 `for` + `setTimeout` 轮询），不能"调用完立刻断言"。

另外：**断言失败时先确认"期望值在几何/数值上可达"**，再怀疑代码。
曾经出现过"从 `#1a1a1a` 起把 G 拖到 10% 期望有变化"，而该色 G 本来就是 26/255≈0.102，取整后字节不变——
"没变化"是正确行为，是断言写错了。

| J2 | `render(src, params, scale)` | 返回 png/pixelJSON/usage/hash，**不改工作区状态** |
| J3 | `edit(ops)` 后再 `undo()` | 可逆；`changes[].changed` 如实 |
| J4 | `validateParams({longEdge:99999})` | 报告被夹紧的字段 |
| J5 | 错误路径 | 无画布导出、色板里没有该色、未知算子 → 抛带中文原因的 Error |

## 3. 报告写法（这是你最终要交的东西）

### 3.1 结论先行

报告开头给一张总表，让人 30 秒看懂：

| 模块 | 用例数 | 通过 | 失败 | 阻塞 | 结论 |
|---|---|---|---|---|---|
| A 导入 | 4 | 4 | 0 | 0 | 正常 |
| B 转换参数 | 7 | 6 | 1 | 0 | 见 P1-01 |
| … | | | | | |

然后给**总体结论一句话**，例如："核心转换与导出链路可用；发现 2 个 P1 问题（X、Y），1 个 P2（Z）。"

### 3.2 问题分级（按影响，不按难度）

| 级别 | 判定标准 | 例子 |
|---|---|---|
| **P0** | 功能不可用 / 数据损坏 / 崩溃 | 导入后白屏；导出文件损坏；工程 JSON 读回数据错乱 |
| **P1** | 主要功能有缺陷但有绕法 | 滑条拖不动只能手输；某格式导入失败 |
| **P2** | 体验/一致性问题 | 提示文案与实际不符；窄屏下按钮被挤掉 |
| **P3** | 观感与打磨 | 间距不齐、颜色不统一、文案生硬 |

**"文档说支持但实际不支持"一律至少 P2**——它会误导用户与 agent。

### 3.3 每个问题必须包含 6 项

````markdown
### P1-01 标题（一句话说清现象）

- **现象**：看到什么（含截图路径或文字描述）
- **复现步骤**：
  1. …
  2. …
- **期望**：应该是什么样
- **证据**：产物哈希 / 控制台报错 / 截图路径 / 断言输出
- **影响**：谁会受影响、有无绕法
- **修改意见**：具体到文件与函数（例：`src/app/ui/colorpicker.ts` 的 `rowFromEvent()`）
````

### 3.4 修改意见要有依据

- 指出**具体文件:行**（用 grep 找到真实位置，不要凭印象）
- 说明**为什么这样改**，以及**会不会影响别的功能**
- 如果涉及已知约束，先读 `docs/ARCHITECTURE.md` §8（已修复缺陷与"别修"清单）与
  `docs/UI-COLOR-PICKER.md` §2（8 条"碰了就坏"约束）——**不要把有意设计当成 bug 报**。
  项目里明确属于"有意为之"的例子：
  - `Del`+`Backspace` 双绑定、工具三入口（键/按钮/API）
  - 用量表 `getUsage()` **不含透明格**（透明格数另有 `countTransparent()`）
  - `trim` 在无透明边时返回 `changed: false` 而不是报错
  - 拼豆色卡是**通用近似色**，不是某品牌官方色号（用户需自行导入官方色卡）
  - **取色器的数值框在滑条轨道之外**（`[滑条轨道][数值框]` 两段结构）——这是**刻意**的：
    防误触靠结构隔离，不靠事件拦截。看到"数字框没在滑条上"不要当布局 bug 报。
  - 色轮方位是**正下方 = 红（色相 0°）、顺时针递增**（照参考图逐像素校准过，不是常规的"正右=红"）

  判断方法：先读该文件顶部的注释与 `docs/` 里的说明，若注释明确写了"有意差异 / 参考图如此"，
  就不要报为问题（可以提"建议改进"，但级别不高于 P3）。

### 3.5 必须包含"未能验证的部分"

如实写清哪些没测、为什么（环境限制 / 缺素材 / 需要人眼判断），**不要静默跳过**。
例如：没有真实照片素材、没有拼豆实体板对照、无法在真机上验证触摸手势。

## 5. 遇到这些情况先怀疑自己的测试，而不是产品

| 现象 | 先检查 |
|---|---|
| 所有拖动断言都失败 | 视口是不是 800×600？左栏有宽度吗？ |
| "元素不重叠""尺寸正常"但显然不对 | 元素是不是 `display:none`（尺寸为 0 会假通过） |
| 点输入框没聚焦 | 用的是合成 `.click()` 吗？无头下不触发聚焦 |
| 画布是空的 | 是不是没轮询等绘制完成？还是视口太小导致画布无尺寸？ |
| 颜色算出来是 `#NaNNaNNaN` | 元素无布局尺寸（rect 为 0）导致除零——这是**真缺陷**，报 P1 |
| 某个值"拖了不变" | 先确认期望值在数值上可达（取整后是否真的会变） |

## 6. 各文件职责（写修改意见时要找对地方）

| 文件 | 职责 | 改动风险 |
|---|---|---|
| `src/core/*` | 纯算法：管线 / 算子 / 导出 / 拼豆 / 元数据。**零 DOM、零 node: 内置模块** | 高（87 项单测守着；在 core 里 import `node:*` 会直接让浏览器构建失败） |
| `src/io/*` | Node 侧平台绑定（PNG 编解码、文件读取） | 中 |
| `src/app/*` | 浏览器：UI、画布、页内 API | UI 改动风险低，但注意不要破坏 `tool/e2e*.mjs` 的选择器契约 |
| `src/app/ui/colorpicker.ts` | 取色器（结构 + canvas 绘制 + 指针交互） | 见 `docs/UI-COLOR-PICKER.md` §2 的 8 条约束 |
| `src/app/style.css` | 全部样式（取色器段落在文件后部） | 低 |
| `tool/*.mjs` | CLI / 构建 / 文档生成 / 端到端 / 截图 / 参考图分析 | 低 |
| `docs/AGENT_API.md` | **由 `src/core/spec.ts` 生成**，不要手改；改元数据后跑 `npm run describe` | — |
