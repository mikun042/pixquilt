# 架构与决策记录

> 本文件面向**后续维护者**。改代码前读它，能省掉一次返工。

## 1. 分层（唯一允许的依赖方向）

```
src/core/*        ←  纯逻辑：零 DOM、零框架、零 node: 内置模块，可被单测与 CLI 直接 import
                    算子相关拆成三个文件：ops.ts（算子语义与状态提交）
                    rasterize.ts（矩形/椭圆/笔刷/直线的几何）canvas-query.ts（外接框/锚点/连通）
                    ops-shapes.ts（描边与镜像的几何辅助）
   ↑
src/io/*          ←  Node 平台绑定（node:zlib / node:fs）——**只允许出现在这里**
src/app/*         ←  浏览器：UI、画布、页内 API、canvas 编码
   ↑
tool/*.mjs        ←  命令行入口（artc 批处理 / build / describe / e2e / serve）
```

**为什么这条线是硬约束**：浏览器包由 `src/app/index.ts` 出发打包。历史上（本项目重写过程中真实发生过）
`core/export.ts` 里放了 PNG 编码，结果它 import 了 `node:zlib`，浏览器构建直接失败。
教训写进规则：**core 里出现 `node:` 前缀就是缺陷**。

验证方式：

```bash
node tool/describe.mjs --write   # 顺带可用 tool 里的依赖链检查（见下）
npx esbuild src/app/index.ts --bundle --platform=browser --outfile=/dev/null
```

第二条命令只要报 `Could not resolve "node:..."` 就说明有人破坏了分层。

## 2. 数据模型

```ts
PixelArt = { width, height, indices: Uint8Array, palette: string[], alphaMask?: Uint8Array | null, frames?: Frame[] | null }
ConvertParams = { longEdge, downsample, cropRatio, paletteMode, paletteK, presetPaletteId, customPalette,
                  dither, ditherStrength, cleanup, cleanupMinSize, brightness, contrast, saturation,
                  transparent: 'none' | 'key' | 'alpha', matteColor, exactWidth?, exactHeight?, lockPalette? }
```

- 索引是 `Uint8Array` → **色板上限 256**，所有色板入口都必须截断（否则重排会回绕出错误颜色）。
- `alphaMask` 为 `null` 表示全不透明（省内存、项目文件回到简洁形态）；全不透明的 mask 会被归一为 `null`。
- `transparent` 三态取代了旧版的 `alpha: boolean` + 独立导出开关：`none` 合成到底色、`key` 单色键控、`alpha` 真透明。
  读取旧文件时 `alpha: true → 'alpha'`，并保留 `alpha` 字段的迁移记录（`sanitizeParams` 会报告）。

## 3. 像素化管线的四条顺序约束（改动前必读）

1. **预处理在降采样之后**：亮度/对比度/饱和度是逐像素仿射运算，与区域平均可交换，在小图上做能省 90%+ 计算。
2. **抖动必须并入量化映射步**：Floyd–Steinberg 要按扫描序把误差扩散给"尚未量化"的邻居，事后处理拿不到那个中间状态。
3. **杂色清理与抖动互斥**：抖动的单像素点正是"杂色"，同时开会把抖动结果吞掉；由 `runPipeline` 强制关闭 cleanup。
4. **OKLab 匹配缓存在抖动开启时必须关闭**：误差扩散后每格的实际输入色带累计误差，缓存会算出错误结果。

## 4. 关键决策（ADR 摘要）

| 决策 | 结论 | 理由 |
|---|---|---|
| 是否保留 React | **不用框架**，vanilla TS + 极简 store | 主体是 canvas + 指针事件 + 直写 DOM；框架的整树协调在这里是纯开销。旧版取色器拖动本来就要绕开 React 直写 DOM |
| 抖动/清理的互斥由谁负责 | `runPipeline` 强制，而非 UI 禁用 | 只要有一条入口（CLI / API）忘了校验，结果就会错；放在管线里对所有入口生效 |
| 色板满时怎么办 | 自由模式退化为 OKLab 最近色并记 `note`；`lockPalette`（拼豆/资产）则**报错** | 拼豆用户不可能买到图纸上没有的颜色，"悄悄换色"是不可接受的 |
| PNG 编码放哪 | Node 在 `src/io/node-png.ts`；浏览器在 `src/app/canvas-png.ts` | 见 §1 的分层教训 |
| 算子放 core 还是 API | core 纯函数 + API 只做校验/提交 | 旧版把 `replaceColor` 的业务逻辑在 UI 与 API 各写了一遍（40 行逐行同构），且行为已分叉 |
| 文档怎么保证不漂移 | `docs/AGENT_API.md` 由 `src/core/spec.ts` 生成（算子/参数/色卡/上限），CLI 参数表在生成时与 `KNOWN_FLAGS` 对账 | 旧版的算子表只活在 Markdown 里，代码改了文档没改，agent 会按错的信息干活。**注意**：`AGENT_API.md` 的"生成物与仓库文件逐字节一致"目前**没有断言守着**（早期文档曾误称有单测比对），需人工重跑 `npm run describe`；见 `DEVELOPMENT.md` §5 |
| 绘制调度 | rAF + 定时器双保险 | 后台标签页/无头环境下 rAF 可能永不回调；只用 rAF 会让画布永远空白（端到端测试真实抓到过） |
| 图集帧尺寸 | **恒等**，用 `offsetX/offsetY` 表达内容偏移，不裁边 | 引擎按固定尺寸切片最省事；帧尺寸不等会让导出侧与引擎侧都要额外处理 |

## 5. 限额与预算（单一出处：`src/core/limits.ts`）

| 常量 | 值 | 为什么 |
|---|---|---|
| `MAX_CANVAS_SIDE` | 2048 | 2048² ≈ 419 万格，索引约 4MB，浏览器仍可交互 |
| `PALETTE_MAX` | 256 | 索引是 Uint8Array |
| `HISTORY_MAX_FRAMES` / `_BYTES` | 50 / 64MB | 只按帧数封顶会让内存随画布面积线性膨胀；两条上限**先到先算**。注意单帧是 `indices + alphaMask` 两份字节，2048² 带 alpha 时单帧 8MB（不是 4MB），所以 64MB 实际约 8 帧。实现见 `src/app/history.ts`（可在 Node 里单测） |
| `MAX_EXPORT_SIDE` / `MAX_EXPORT_PIXELS` | 16384 / 64M | Chromium 硬上限附近，按面积再夹一道 |
| `ALPHA_THRESHOLD` | 128 | 全项目唯一的透明判定口径 |
| `MEDIAN_CUT_SAMPLE_LIMIT` | 250k | 切分是统计性聚类，几百万像素只会让盒内排序白白变慢 |

## 6. 性能

- 取色对 >250k 格抽样（固定散列步长，保证"同图同参 → 同色板"）。
- 量化在关抖动时使用直接映射缓存（≤2^15 槽），开抖动时禁用。
- 绘制：笔画期间只改本地副本，抬笔才提交一次（一条撤销）；画布内容缓存进离屏 canvas，只在内容变化时重建。
- 大画布往返用 `.pixbin`（12 字节头 + 索引 + 可选 mask），比 base64 项目 JSON 快一个量级。

## 7. 怎么验证一个改动是安全的

```bash
npm run verify     # 七步全绿才算通过；每一步的说明见 docs/DEVELOPMENT.md §3
```

**测试有效性的判断标准**（比数量重要）：故意改坏一处，看测试是否变红。本项目已用这个方法验证过的断言包括：

- 无副作用的 `render()` 不继承主色 → 改成继承后，`--selftest` 的"无副作用路径"相关断言会失败；
- `changed` 漏判"只改 alpha 的挖洞" → 单测与自检都会红；
- 抖动与清理不互斥 → 单测"抖动开启时清理被强制关闭"会红；
- 绘制只依赖 rAF → e2e 的"画布真的画出了内容"会红（headless 下 rAF 不产帧时）；
- 算子表与实现漂移 → 单测"spec.ts 列出的算子与实现完全一致"会红；
- 量化缓存复用错误索引 → 单测"缓存路径与逐格直接匹配必须逐位一致"会红；
- 空状态提示盖住画布 → e2e 的"导入图片：转换结果真的显示出来，且空状态已移除"会红；
- `cleanup` 报告恒为空 → 单测"cleanup 吃掉的颜色必须如实上报"会红；
- 页面宣称的算子未实现 → e2e"每个算子都真的能执行"会红（让 `mirror` 抛"未知算子"即可复现）；
- 两个面板折叠状态存成单值 → 回归断言"能同时收起（不再互相顶开）"会红。

写新断言时，请把对应的"改坏方式"一并写进提交说明——这是本项目判断测试价值的唯一方式。

## 8. 修掉过的真实缺陷（都是静默的，值得记住）

### 8.1 「导入图片转换不出来」——不是转换问题，是遮挡

空状态提示曾写死在 HTML 模板里，而它自带不透明背景并铺满画布区域（`.empty-state{inset:0}` + `.canvas-host` 的渐变背景）。
导入成功后**没有人移除它**，于是它一直盖在画好的画布上：数据全部正确（`hasArt: true`、色板正常、画布确实画了 11 万像素），
用户看到的却是"没反应"。

**规则**：任何覆盖在画布之上的浮层都必须有明确的移除条件，并为此写一条断言。
诊断这类问题的最快路径是**分清"数据对不对"与"看得见看不见"**——先读 `getInfo()` 再看 `dataset.draws`，
两步就能定位到层叠而不是算法。

### 8.2 固定色板下整幅图只剩一种颜色——量化缓存静默复用错误索引

量化缓存最初的设计是"按 RGB 截断值当槽位，命中就直接复用索引"。问题在于**只校验了截断键（每通道 5 bit）**，
于是 top-5-bit 相同的两个不同颜色会共用同一槽位、拿到同一个最近色索引。实测 1200 格里错 4 格，
在更大反差或更强压缩的图上可退化成整幅单色——而且不报错、不警告。

**修法**：槽位仍用截断键寻址（快），但命中时必须校验**完整 RGB**（`fullKeys[slot] === full`）。
三个平行数组（`slotKeys` / `fullKeys` / `cacheIdx`）比"把键与索引打包进一个整数再用位移比较"更不容易写错：
**缓存的正确性必须能用一句话说清**。

**验证方式**：单测把"带缓存的 `quantize()`"与"独立实现的逐格最近色匹配"逐位比对（这是真正的交叉验证，
不是自己和自己比），再加一条"渐变图在 16 色固定色板下至少用到 4 种颜色"。

**教训**：凡是"为了快而做的近似"，都必须有一条与独立实现交叉验证的断言；
只做"跑通不报错"的测试，抓不到这类静默错误。
### 8.3 取色器（Blender 结构）重构时踩到的坑

按用户要求把取色器改成 Blender 取色界面的结构（色轮 + 明度竖条 + 透明度横条 + RGB/HSV/Hex 标签 + 色板）时，
一次改动连续暴露了四类问题，全部已修并写了断言：

1. **面板重建导致实例失联**：取色器的宿主元素原先跟着 `renderPalette()` 一起重建，而实例的 DOM 仍挂在旧宿主上。
   表现为"打开正常、一拖动就消失"（拖动会触发一次重渲染）。→ **宿主元素改为模块级持久化**，渲染时只清色板的子节点。
2. **零尺寸几何产生 NaN**：侧栏收起或面板不可见时 `getBoundingClientRect()` 全为 0，除零后 NaN 沿色相/饱和度
   一路污染成 `#NaNNaNNaN` 这种非法颜色写进主色。→ 所有"指针坐标 → 几何比例"换算都加了 `width/height > 0` 守卫。
3. **`setPointerCapture` 抛异常打断处理器**：pointerId 不是活跃指针时（合成事件、部分触控设备）会抛 `NotFoundError`，
   而它位于处理器开头，一抛后面的取色逻辑就整段不执行。→ 统一走 `safeCapture()` 吞掉异常。
4. **滑条端点判定过于严格**：`getBoundingClientRect()` 返回小数，鼠标落在最左 1px 处算出的比例是 0.006 而非 0，
   用 `<= 0.001` 判定"拖到最左"基本点不中。→ 先引入 6% 死区（`ALPHA_ZERO_ZONE`）；
   **后来又被这一版自己推翻了**：死区只有最左 6%（128px 轨道上约 8px），用户拖中段毫无反应，
   反馈成"这条滑条拖不动"（实测 0.9→0.2 的值纹丝不动）。现在换成**中线分界**
   （`ALPHA_MID = 0.5`，左半 = 透明 / 右半 = 实色）——整条轨道都有响应，两个方向都实时翻转。
   教训：**"让极小的一段有特殊含义"在细窄控件上等于没有交互**，宁可把分界放在人能看见的地方。
   同时这一行的数值也从 `Alpha 1.000`（不透明）改成 **`透明度 0.000`（不透明）/ `1.000`（全透明）**——
   全界面只有它原来用 alpha 口径，与"透明色/透明挖洞"的语言打架。

**另一条方法论教训**：这些问题的复现与否取决于视口大小——我的验证脚本一开始用 headless 默认的 800×600，
命中 ≤980px 的窄屏规则把左栏 `display:none`，色轮因此没有布局尺寸，所有拖动断言全部失真。
→ 验证脚本必须先 `Emulation.setDeviceMetricsOverride` 设成桌面视口，并断言左栏确实有宽度。
**UI 断言必须先把环境摆成它成立的样子**，否则测的是环境而不是产品。

**第三条教训（2026-09-13）**：合成 `PointerEvent` **绕过命中测试**，所以"元素被盖住/命中区变小"
这类问题它能全绿通过，而用户拿真实鼠标一点就废。同一类问题（滑条数值框误触、Alpha 拖不动、
拖拽选中文字）全部要用 CDP 的真实输入（`Input.dispatchMouseEvent`）复现——
`tool/e2e-picker.mjs` 里的"拖动滑条不会选中沿途文字"就是这么测的。

取色器专项验证在 `tool/e2e-picker.mjs`（17 项）、数值滑条专项在 `tool/e2e-slider.mjs`（12 项），
两者都已并入 `npm run verify`。

### 8.4 数值滑条"划不动"——两个叠在一起的原因

另一位 agent 按参考图把数值行改成了"整行填充条 + 归一化小数"（RGB/HSV/Alpha 同一形态），
但用户反馈 **RGB 与 HSV 滑条拖不动**。排查发现是两个独立问题叠在一起：

1. **六行根本没绑拖拽事件**：只给 Alpha 行写了 `pointerdown` / `pointermove`，
   R/G/B/H/S/V 六行只有文本输入的 `onchange`——看上去是滑条，实际上只能手输数字。
   → 抽出 `setChannelRatio(key, ratio)` 作为**唯一设值入口**，拖动与手动输入共用；
   再给六行统一绑指针事件（与 Alpha 行同一套写法，含 `safeCapture` 与零尺寸守卫）。

2. **改一个通道经过两次往返会"弹回去"**：最初实现是
   `hex → RGB → 改字节 → HSV → hex → RGB`，而 HSV⇄RGB 与 hex 解析各自都要取整，
   ±1 误差叠起来会让值回到原字节——实测把 G 拖到 0.1（期望 26）算回 26，表现为"怎么拖都不变"。
   → 把 **hex 作为字节级真源**（`currentHex`）：RGB 操作直接改字节、只在最后反推一次 HSV；
   HSV 操作（色轮/明度/H·S·V）改 `hsv` 后调用 `syncHexFromHsv()` 写回。
   全部 `cb.onPreview` / `cb.onCommit` 都传 `currentHex`，保证"显示值 = 提交值"。

**测试数据也要讲道理**：新增的 `tool/e2e-slider.mjs` 一开始从 `#1a1a1a` 起拖 G 到 10%，
而该色 G 本来就是 26/255≈0.102——取整回同一个字节，**"没变化"是正确行为**，却让断言误报。
改为从 `#808080`（三通道都在中位）起步，每个通道才有足够行程。
**断言失败时先确认"期望值在几何/数值上可达"**，再怀疑代码。

回归防线：`tool/e2e-slider.mjs`（10 项：六行逐行拖动、标签切换后的显隐、手动输入、
连续拖动、零尺寸免疫），已并入 `npm run verify`。

### 8.5 未知参数被静默忽略——比报错更糟的一类失败

外部 agent 用 `--exact 32x32` 指定尺寸，命令**成功退出**，产物却是默认 64×64。
原因：`--exact` 不是任何已实现的 flag，于是它进了没人读的 `args.exact`，
`32x32` 落进同样没人读的位置参数 `_`，两者都不报错。

**为什么这类失败特别贵**：调用方（尤其是 agent）没有"命令失败"这个信号可用，
只能拿产物继续往下走，直到下游发现尺寸/颜色不对才回头怀疑引擎——
此时已经很难判断到底是引擎错了还是自己用错了。定位这条时我自己也踩了同一个坑，
跑完两轮基于错误尺寸的实验才发现参数根本没生效。

修法不是"少写几个参数"，而是**把沉默变成硬错误**：`assertKnownFlags` 拦截所有未登记参数，
按编辑距离给出最接近的正确参数名，并额外提示"它还吞掉了后面的 `X`"——
后者专门用来暴露"参数名写错导致值被当成位置参数"这一模式。

同源教训：`BOOL_FLAGS` 上方原本就有注释写着"不要往这里加没有实现的 flag……静默失效比报错更糟"，
但**只靠注释约束不住**。现在有 `artc --selftest` 的双向断言（帮助提到的必须在允许集里，
允许集里的必须在帮助里）——加这条断言时它立刻抓出了我自己漏登记的 `--blank-transparent`。

### 8.6 `--json` 的输出不是 JSON

`--json` 存在的唯一理由是"给机器读"，但它把人类进度行（`✔ 空白画布 …`）和 JSON 一起写进
stdout，首字符是 `✔`，于是 `JSON.parse` / `jq` / `ConvertFrom-Json` 全部直接失败。
这是"名义上提供了机器接口、实际上不能用"的典型。

修法：`--json` 默认静默，stdout 只剩一份 JSON；要同时看进度加 `--progress`，进度写 stderr。
**判据**：一个开关如果声明自己是机器接口，它的 stdout 就必须能被严格解析——
这比"人多看一行也无妨"重要得多。

### 8.7 工具脚本被 import 时会执行 `main()`

`artc.mjs` 末尾直接调用 `main()`。任何 `import './artc.mjs'`（例如只想读一下
`KNOWN_FLAGS` 做一致性检查）都会顺带跑一遍 `main()`，而它读的是**导入方**的 `process.argv`——
要么误处理参数，要么报错打印帮助并 `process.exit(1)`，把导入方一起带走。

这类缺陷的隐蔽点在于：**症状出现在调用方，根因在被导入方**。当时表现为
"一个只打印四行统计的检查脚本什么都不输出、退出码 1"，排查方向很容易跑偏。

修法：`process.argv[1]` 与 `import.meta.url` 比对后再执行。副作用是本文件变得可被直接导入，
测试不必再 spawn 子进程——把 `tool/` 下的脚本都当作"可导入的模块 + 可执行的入口"来写更稳。

### 8.8 「新建」点不了 + 找不到空白画布入口——第一次使用时的死路

用户反馈三件事：没导入图片时「新建」点不动、不知道怎么建空白画布、「工具/参数」按钮按了没反应。
前两件是**同一个死路**：

- `updateHeaderState` 里写着 `newBtn.disabled = !art && !src`——没有画布就把「新建」变灰。
- 而唯一的"新建空白画布"入口挂在**「导出 ▾」菜单**里。第一次打开的人不会去"导出"里找"新建"。

于是新用户看到的是：正中间写着"导入图片"，唯一带"新建"字样的按钮是灰的。
**这不是功能缺失，是入口与命名的问题**——功能一直在，只是放在了错误的心理模型下。

修法：不要再试图"引导用户去导出菜单找新建"，而是让它名副其实——
`新建` 在没有画布时**直接建一张**（有画布时才保持原来的"确认后清空"语义），
同时空状态里直接给出「✚ 新建空白画布」按钮。三处入口指向同一件事，用户从哪儿进都行。

### 8.9 `.narrow-only` 只有类名、没有规则——"按了没反应"的按钮

顶栏两个抽屉开关带着 `class="btn narrow-only"`，意图显然是"只在窄屏显示"。
但全仓库搜索 `.narrow-only` 只有三处命中：两处是 HTML，一处是**注释**里提到它。**没有任何 CSS 规则。**

后果有两层：

1. 宽窗口下按钮照常显示（那个类名什么也没做）。
2. 宽窗口下点击只改 `dataset.drawer`，而桌面布局根本不读这个状态——
   按钮看起来正常、hover 有反应、点了**什么都不会发生**。

这是本项目第 N 次遇到同一模式：**没有错误信号，只有错误结果**。
和 8.1（遮挡）、8.2（缓存复用错索引）、8.5（未知参数静默忽略）是同一种病。

修法上做了一个选择：**让它在两种宽度下都真的有用**，而不是补一条 `display: none` 把按钮藏起来。
理由是"显示/隐藏面板"这个动作在两种宽度下都成立，只是形态不同（宽屏折叠常驻列、窄屏开合抽屉），
用户的心智模型是统一的。桌面折叠用改 `grid-template-columns` 实现而不是 `display: none`——
面板是网格列，直接隐藏会让后面的列左移串位。

教训不是"记得写 CSS"，而是：**一个类名如果意图是"控制行为"，就必须有对应的断言**。
现在 `e2e-regressions` 里有三条锁住这两个交互（含真实鼠标点击，
因为合成 `.click()` 绕过命中测试，测不出 `pointer-events` 与遮挡问题）。

> **后续（2026-09-14）**：这套开关最终搬到了**栏外的画布边上**（画布左上角 / 右上角，
> 紧贴对应侧栏的边），图标改成三角形箭头（展开时指向收纳方向、收起后指向展开方向），
> `.narrow-only` 这个类名随之删除。放栏外而不是栏内的原因是：栏内的话面板一 `display:none`
> 开关就跟着没了，只能让面板收成一条窄边来"顺便"留住开关（空窄边白占宽度）；
> 浮在栏外则面板可以真正收干净、开关永远在原地（栏收起后它自然贴到画布/屏幕边缘）。
> 由此带出两条必须记住的 CSS 约束：**隐藏一栏时必须同时把 grid 模板改成两列**
> （`display:none` 会把网格项摘出布局、剩下两项自动重排，只改 display 会让画布宽度变成 0）；
> **滚动容器换成内层 `.rail-body` 时必须补 `min-height: 0`**
> （grid/flex 子项的自动最小高度是内容高度，漏了会让面板不再滚动、页面反而变长）。

**修完当场就翻的车**：把按钮改成"桌面折叠侧栏"之后，折叠状态存的是
`let desktopHidden: 'none' | 'tools' | 'panel'`——**单个三值变量**。
于是四个组合里"两边都收起"不可达：收起工具列后再收参数列，赋值 `'panel'` 顺手把
`'no-rail'` 摘掉了，工具列又弹回来。用户报的就是这个（"关第二个时第一个会打开"）。

单值状态**在类型上就表达不了"这一对独立开关"**，这跟字符串拼 key 是同一类错误：
编码方式本身丢掉了信息，写的人却以为状态是完整的。改成两个布尔量后，
CSS 里原本永不可达的 `body.no-rail.no-panel` 才第一次有了意义。

顺带收紧了那条组合 CSS：它原本与单条规则**同权重**，靠源码顺序取胜，
顺序一动就静默失配（两栏都隐藏、网格却留着空列）。改成加一级特异性，不再依赖顺序。

新增断言特意**成对检查"另一个没被顶开"**——只测"单独折叠生效"是抓不到这个 bug 的，
这也是它当初从 22 条断言里漏过去的原因。

### 8.10 四类"假功能"：没接线 / 没绑定 / 没消费 / 没通知

静态审阅与运行期探针（2026-09-14）翻出四处**代码齐全、样式齐全、用户点了没反应或反应错了地方**的功能，
它们与 8.1/8.2/8.5/8.9 是同一种病：**没有错误信号，只有错误结果**。
四处的"缺环"位置各不相同，正好构成一张排查表：**生产者 → 触发器 → 消费者 → 通知**，缺哪一环都是死的。
前两处来自静态审阅（读代码就能发现），后两处来自**运行期逐控件验证**（读代码发现不了）。

**① 放大镜（"原图对照"）从来没接线 —— 缺生产者**。canvas 侧的取景、绘制、容器注齐全都在，
但唯一的开关 `setReference` **全仓没有调用点**：canvas 内部的 `refImage` 恒为 null，
而 `updateMagnifier()` 的第一个守卫就是它，于是放大镜永远不出现。
更隐蔽的是**参数面板里有个"笔刷预览 / 放大镜"的勾选框在承诺它**（勾选框本身有效，
只是它控制的另一半——放大镜——是死的）。
实测确认方式：导入图片 → 真实鼠标悬停画布 → `#magnifier` 仍是 `display:none`。
诊断手感：**先分清"数据对不对"和"看得见看不见"**（8.1 的老办法）——
`getInfo().hasArt` 为真、色板正常，问题就落在"没人调用那个开关"上。
修法：`setReference`/`attachMagnifier` 提升为 `CanvasApi` 的正式方法（原先靠 cast 事后挂载），
导入后调 `setReference(img, false)`（`false` = 只启用放大镜，不把原图半透明叠上去）。
断言用**真实鼠标移动**触发悬停，并同时断言"放大镜里真的画了内容"——
只看 `display:block` 的话，画布空白同样会漏过去。

**② 画布右下角的视图工具栏没有事件绑定 —— 缺触发器**。`适配 / 100% / − / ＋` 四个按钮在 HTML 与 CSS 里都在，
但全仓没有任何 `getElementById('view-…')`——而 canvas 侧恰好**已经有** `fitView` / `zoomBy` /
`zoomToCell` 三个方法、外部调用数为 0。两边都在，就是没接上。
修法上做了一个选择：**整条删除**而不是接线——这四个动作已被快捷键完整覆盖
（`0` 适配、`+`/`−`、滚轮、空格/中键平移），留着只是多一处要保持同步的入口。
删完补了一条**防回归**断言：`.view-toolbar` / `#view-*` 不应再出现。

**③ 合成底色吸管的 `pickIntoMatte` 没人消费 —— 缺消费者**（本轮新发现，形态最像"能用的"）。
入口、按钮、提示语、状态赋值全都在：点取色盘里的吸管 → `pickIntoMatte = true` → 弹出
"到画布点一格，颜色会填到「合成底色」"。但全仓唯一的"读取"是 `toast` 里那句文案本身——
画布的 `onPickColor` 从不看这个标志，于是颜色**悄悄写进了主色**，合成底色纹丝不动。
它比 ①② 更难发现：功能**确实有反应**（主色变了），只是反应在错的地方，而提示语还替它担保。
诊断方式：**对每一个"待办标志"做一次全仓单向核查**——赋值点有几处、读取点有几处；
`grep pickIntoMatte` 的结果是 4 处赋值 + 0 处消费（文案里那次读取不算）。
修法：`onPickColor` 里消费该标志（写进 `matteColor`、把颜色记进"最近"、还原进吸管前的工具）。
同一段提示语里还有一句"（Esc 取消）"，而 Esc 原先只是清选区——顺手一并兑现（退出吸管、还原工具），
免得修好了去向、却留着半句空头承诺。
断言用**真实鼠标走完整链路**（取色盘吸管 → 画布点一格），且断言的是"颜色去了哪一路"：
只断言"点击有反应"的话，错误实现同样是绿的。

**④「显示」区的勾选框改了状态、没人通知画布重绘 —— 缺通知**（本轮新发现，只有跑起来才看得见）。
生产者在（`store.set('showGrid', …)`）、消费者也在（`draw()` 里读 `store.get('showGrid')` 决定画不画网格），
缺的是**中间那一跳**：`store` 只通知关心该 key 的订阅者，而唯一的 `showGrid` 订阅者是"写本地偏好"，
画布却是在 `draw()` 里读它——于是勾掉「网格线」后网格**留在画面上不动**，直到下一次无关的 `renderAll`
才突然跟着变（表现为"勾了没反应，过一会儿自己好了"，比彻底失效更难归因）。
`showMag` 同理（它同时管笔刷足迹预览与放大镜）。
诊断方式：**别只看状态位，要看副作用**——`store.get('showGrid')` 是对的（`false`），错的是画面。
实测手段：点勾选框前后读 `board.dataset.draws`，一个都不涨即确诊；再用"画布墨量"
（把 board 抄进离屏 canvas、累加不透明像素的红通道）对比画面是否真的变了。
> 探针本身也踩了一个坑，值得记下：第一版用**白色**画布测，得出"网格根本没画"的结论——
> 而网格线是 `rgba(255,255,255,0.10)`，**白底上肉眼与像素都分辨不出**。换成黑底才看到真实差异
> （墨量 1406343 → 277507）。**测量工具的前提错了，结论会朝错误的方向指得非常自信。**
修法：两个勾选框的 `onchange` 里补 `canvasApi.redraw()`（不必整面板 `renderAll`——勾选框自身状态是原生的）。
断言同样用真实鼠标 + 墨量对比，而不是读那个本来就对的布尔值。

**四条通用教训**：
- 一个功能"实现完了"不等于"能用"——**从入口到实现之间那条调用链，必须有人验证过**；
  写功能的人容易只测自己刚写的那个函数（`setReference` 本身没 bug）。
- 界面上任何"承诺了某个能力"的控件（勾选框、按钮、菜单项），都必须有一条断言锁住它的效果；
  否则它会安静地变成谎言，而用户只会说"点了没反应"，让人从错误的方向排查。
- **标志位必须成对出现**：设置它的地方和消费它的地方要能互相指认（注释里写明"消费在 X"）。
  只写不读的标志比死代码更危险——死代码至少不撒谎，而它会连带一句提示语一起撒谎。
- **状态对了不等于画面对了**：状态是"因"，画面是"果"，中间的"通知"是一段独立代码，也会漏。
  验证这类问题必须断言**可观测的果**（像素、DOM 属性），而不是断言你用肉眼确认过的那个因。

## 9. 仍未做的事（诚实清单）

完整的路线图见 `docs/DEVELOPMENT.md` §8（含价值/风险/做法建议）。这里只列与本文件相关的结构缺口：

- **多帧动画**（数据模型已预留 `frames`，UI/API/导出均未暴露）。**用户明确说"后续再加"，别抢跑。**
